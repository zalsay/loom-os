# 人工发布执行与复盘

与内容制作分开管理；不运行发布脚本，不登录账号，不配置自动任务。

- [发布前核验清单](发布前核验清单.md)：事实、素材授权、配图和复制文案检查。
- [发布记录](发布记录.md)：历史记录与本轮未发布项分开。
- [数据记录模板](数据记录模板.csv)：人工填入后台原始字段，不编造缺失指标。

## 记录规则

先填平台、链接、准确发布时间、标题版本和首图版本，再登记观察时间。24 小时和 72 小时是本批选用的观察节点，不是平台流量周期保证；未发布的内容不填假日期。

曝光、浏览和打开等字段按后台实际名称记录。没有的数据写“未提供”，不要填零；收藏、评论和主页访问等也只在可获得时记录。

如需计算 CTR，先确认分子、分母属于同一统计口径与时间窗口；已有官方显示值也按截图原样登记。不同片长的视频要分开比较，低样本只做观察，不宣称显著结论或算法因果。

评论提问和跨平台复用依实际需要进行。不要为了完成动作清单强行互动，也不声称同步发布能带来固定收益。

## 发布事实四分法

发布状态必须拆成四件事分别记录，不得互相替代：

1. **操作员指示**：谁、何时、以什么方式授权或要求登记（消息/口述）。只证明意图，不证明平台状态。
2. **提交回执**：上传成功、定时提交成功、`publish/success`、`/post/list` 显示“将于…发表”等。只证明提交，不证明已公开。
3. **实际公开**：平台后台或公开页确认已发出、可见、共几条。
4. **后台精确时间 + 链接**：分平台记录；拿不到就写“未提供”，不补猜。

- “定时时间”不是“公开时间”；“提交回执”不是“已公开”。
- 主状态写“已发布”至少要有第 3+4 项；只有操作员确认时，写“已发布（操作员确认）”并在备注保留缺证事实。

## 四项独立勾选

以下四项逐项独立，任何一项都不能由另一项推导：

- [ ] 技术验收（版本哈希、解码、抽帧/扫描）
- [ ] 人工试听（音画同步、发音、BGM 平衡）
- [ ] 全片隐私复核
- [ ] 发布授权

已知路径按现状接受时，必须写清 **“已知路径按现状接受（范围：…；时点：…；确认人：…）”**，这只是风险接受，不等于已完成隐私复核；不得把“接受”勾成“已复核”。

## 单写者制

- 同一台账同一时点只允许一个写者，其他成员只读复核；发现漂移先报告，不并发回写。
- 工作日志保持 append-only，不回填历史时点；更正另起一条，注明更正对象。

## 去重对账

- 发布前必须查两平台是否已有同素材：成片 md5/SHA-256、标题、定时记录。
- 暂停、移交或恢复发布后，先对账再操作。
- 重复风险只写“条件风险”；未取得后台证据，不得写“已双发”或“已无重复”。
- **未在平台后台核验确认前，严禁删除或取消唯一线上帖子**：哪怕怀疑重复，也先截图留证、核对链接与条数，再报告操作员决定；误删唯一帖子不可逆，不能靠“重发一次”补救。

## 复盘口径隔离（硬防线）

复盘前先给每个数字贴三张标签，缺一张就不许写进结论：

1. **统计层级**：`单篇` / `账号合计` / `系列合计`。账号日表的数字是当日全部视频之和，**不得**当成某一集的首晚播放；系列合计不得拆回单集。
2. **数据窗口**：起止日期 + 该字段的刷新时点（实时 / 数据更新至 00:00 / T+1 / 累计）。不同窗口的数不得并列比较。
3. **证据**：官方导出件、单篇页、后台截图或 OCR，写清文件名与时点；没有证据的字段写“未提供”。

附加规则：

- **单篇数据只取单篇字段**（单篇视频表、单篇详情页、官方导出逐条），不得由账号合计反推或拆分。
- **均播 ÷ 片长 = 平均观看占比**，不是留存曲线，不能用来定位“第几秒掉人”，也不能单独证明开头/结构是原因。
- **CTR 只认官方字段原值**；缺分子、分母或刷新时点时标“待核”，不得自算替代，也不得因自算值不同就判官方字段“矛盾”。
- **三道门分开记**：分发（曝光/推荐量）→ 点击（封面 CTR）→ 留存（2 秒退出率/均播/完播）。每道门单独下结论，不合并成“播放量不好”。
- **事实与假设分栏**：可核字段进“事实”，归因与推测进“假设”，并写明可检验方式。

## 证据优先级与冲突处理

四类证据的采信次序（高 → 低）：

1. **平台后台截图 / 提交回执**（`publish/success`、`/post/list` 记录、后台公开页截图）
2. **当日执行日志**（SOP / 工作日志中当场写下的操作记录）
3. **聊天转述**（成员事后复述“当时好像点了…”）
4. **推测**（“应该已经发了”）

- **适用范围**：优先级只在**同一对象、同一待证事实、相近时点**下成立；跨对象（不同帖子/不同平台）、跨事实（“谁提交的” vs “平台是否公开”）、跨时段（提交之后又发生了新操作）不套用本条，应分别取证。
- **提交回执不能否定其后的人工发布确认**：回执只证明“那一刻提交成功”；若其后操作员在后台人工发布了同一帖子，以更新的后台/公开状态为准，并在备注保留两次动作的时点。这与「去重对账」里“未在后台核验前不得断定状态”是同一条原则的两面。
- 低优先级证据与高优先级冲突时，以高优先级为准；备注里写明冲突项与各自时点，**不得用转述覆盖回执**。
- 转述可以解释“为什么这么做”，不能证明“平台实际是什么状态”；状态栏仍按四分法填。
- EP07 即为例：操作员 20:38 指示属第 3 类（证明意图），视频号 20:41 / 小红书 20:48 的提交记录属第 1 类（证明提交），实际公开时间与链接仍待后台核验。

## 双平台文案与搜索（SEO）规范

每集文案需根据平台生态定制，杜绝一套文案机械通发：

### 1. 微信视频号专属规则（社交裂变 + 搜一搜长尾）
- **移动端前 2 行防折叠法则**：视频号信息流简介在移动端展示通常只有前 2 行（约 30–40 字），其后即被折叠为“...全文/展开”。**首两行必须独立成段**，直接抛出反差冲突、悬念或核心问题，打破用户划走惯性；不得在首两行写客套废话或背景铺垫。
- **圈层分享诱饵（撬动算法最高权重）**：视频号算法核心权重为“转发/分享 > 完播率 > 评论 > 点赞”。科技与硬件类内容主要靠熟人群聊转发撬动推荐，正文结尾必须设计具体的**行业/圈层探讨切口**（如询问软硬件联调经验、极客选型等），激发工程师、创客与科技家长在微信群中转发讨论。
- **微信“搜一搜”三级 SEO 标签矩阵**：
  1. *品牌主词*：`#织界` `#LoomOS` `#Mosaico`（沉淀品牌心智）
  2. *硬件/技术长尾词*：`#硬件研发` `#单片机开发` `#嵌入式日常` `#创客日记` `#真机实测`（命中技术长尾检索）
  3. *少儿科创高频词*：`#儿童编程` `#STEAM教育` `#AI教育` `#探索式学习` `#科技养娃`（命中高净值家长搜索流）
- **置顶评论与冷启动参考建议（待操作员逐条批准后执行）**：
  - *第三方推测声明*：互动率与流量池阶梯属于行业自媒体推测，非官方保证；
  - 发布后是否配置置顶评论由操作员批准决定，模板以真实技术小结与低门槛交流为主，不为硬凑互动虚构争议；
  - 私域种子分享须依真实兴趣自然进行，严禁组织化刷量。

### 2. 小红书专属规则（真实工程探索 + 视觉化排版）
- **真实工程切入（严禁虚构孩子在场）**：无孩子参与的机录素材严禁写成“带孩子上课”；应从“孩子未来面对的真实工程探险”视角切入，将复杂的排查降维翻译为严谨探索的态度价值。
- **视觉化排版**：适度采用 Emoji 标点、分段留白，重点句子用标号或重点符号框出，降低阅读负荷。
- **结尾开放思考**：留出探索态度维度的探讨问答，引导评论区自然互动。

## 纯中文叙事与语言硬防线

1. **旁白 100% 纯中文**：旁白逐字稿严禁夹带任何英文专业词汇（如 `nonce`、`partial`、`capabilities`、`stdout` 等）；必须全部汉化为精准、通俗的人话（如“专属报告槽”、“部分完成”、“底层基础接口”）。
2. **字幕与说明条纯中文**：自制字幕、顶部标题、后期说明条与悬念胶囊必须全部采用中文，杜绝中英文混杂与 AI 电报体。
3. **真实证据原样保留**：终端机录日志中的原始英文（如命令回执、字段名）属于事实证据，客观保留其真实性；中文在说明浮层和旁白字幕中承接与解读，严禁翻译重绘伪造终端日志。
