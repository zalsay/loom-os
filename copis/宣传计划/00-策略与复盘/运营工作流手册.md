## WF-1 数据采集

**触发**：用户授权的采集任务、发布后观察节点或日常复盘；不因本手册自行创建定时任务。

1. 使用已有授权的 Chrome 桌面环境与 mcc。先核对权限、窗口和运行状态；需启动服务时用受管理的后台任务运行 `mcc daemon run`，不把 `daemon start` 成功当作服务持续存活证明。
2. 双平台作品列表优先使用官方导出按钮获取 CSV 并用 Python 统计：小红书「内容分析→导出数据」，视频号「单篇视频→下载表格」。账号总览、日表、来源、关注者与导出未覆盖的详情仍单独采集。平台警告、登录失效或用户暂停时停止，改由用户提供截图/导出，不换通道绕过。
3. 导出前记录账号、作品筛选、字段、统计范围、页面总数及实际采集时间并留截图；核验下载完成、文件来源、实际格式及覆盖范围。原文件原样保存到当日证据目录，唯一命名、不覆盖；若平台实际输出非 CSV，保留原件，按实际格式读取或转换成单独的派生 CSV，记录转换方法，不能只改后缀。
4. 用 Python 读取 CSV，核对编码、分隔符、表头和单位，正确处理 BOM、引号、数字分隔符、百分号及缺失值；保留原始字段及原值。校验导出行数、作品身份、重复、必要列、空值与异常，和页面总数及样本数据核对，确认是否覆盖全部分页；保存可复现的统计方法或脚本/命令、结果和缺口。未提供、解析失败或空值不能记为零。
5. 落盘至 `copis/笔记数据/YYYY-MM/`，保留证据原始导出、筛选截图及必要详情、采集时间、数据截止点、平台字段原名、单位与统计窗口。导出缺列、无法下载或解析时记录原因并优先请用户提供官方导出；可在授权内补充页面截图/详情，不能宣称 CSV 统计完成。
6. 视频号账号日表、单篇选定窗口和详情累计分别读取；登录操作在用户授权内进行。出现数字不一致先登记口径疑点；不得用观看÷曝光替换官方 CTR，不跨平台相加，不把百分比或均值简单求和，不以滚动近 7 天表冒充全历史累计。

### 每日数据必查与验收（2026-10-30 补充）

- **范围先行**：用户未明确缩小范围时，视频号每次须覆盖账号全部已发布视频，先核对内容管理全部作品数、身份与发布时间；默认近7天、单页及其筛选总数不能代表全账号。使用可覆盖全部作品的筛选或按允许的时间分段导出，按视频 ID 对照全量清单、核对分页及缺漏；跨段重复作品按统计口径和导出时点核实，不能盲目相加。平台限制导致无法全覆盖则逐项报告缺口，不宣称完成。记录本次采集时刻、账号与作品身份、所选近7天/近30天或自定义窗口、统计起止与平台更新时间；账号总览、账号每日、单篇所选窗口和详情累计快照分开。页面未给字段的起止或累计口径就注明“未标明”，不猜。
- **视频号分享必须逐篇采集**：先用「视频数据→单篇视频→下载表格」官方导出并用 Python 核验原字段「分享」、作品身份和范围；导出缺列时再用字段选择、横向滚动或已授权详情补齐。详情中的「转发聊天和朋友圈／设为铃声／设为状态／设为朋友圈封面」如可用也分项记录。单篇分享、账号每日分享、来源分布中的分享来源播放是不同指标，不互换、不重复加总，详情分项和列表总数之间的关系以平台说明为准。
- **小红书互动必须逐篇采集**：优先从「内容分析→导出数据」的官方文件用 Python 读取各篇点赞、评论、收藏、分享及涨粉；账号概览的互动总数、各分项、单篇列表和详情分别留证。导出缺字段时从已获授权的详情补齐；无法访问时由用户提供截图或导出，未提供一律写“未提供”，不得补零。区分官方首评与真实观众评论，不凭评论总数推断归属；账号互动总数不能自动分配给单篇，不能假定其统计规则等于分项简单相加。
- **完成性检查**：同时核对两平台“应采作品数／已采／未采”、页面总数、导出行数、字段覆盖、所选范围、是否覆盖全部分页及证据链接；导出经核验覆盖全范围时无需逐页截图。缺列、覆盖不明、平台限制或证据不足须标“部分完成”，写明待补项目与责任人。更新历史快照用追加补录并标注**实际导出或截图时间**，不能覆盖旧采集时点，也不拿昨日日表替代实时或累计数据。对照原始导出或截图核实结果；保留原始证据、Python 统计方法、平台字段名及窗口，使用 `04-发布执行与复盘/数据记录模板.csv` 的逐字段口径记录。

**操作纪律**：截图路径唯一；事件投递后重新观察并核对回显。连接是否能跨命令复用按实际状态判断，不把某次失效泛化成硬限制。坐标依据本次原尺寸 frame；屏幕原点、裁剪偏移与显示缩放分别换算，禁止硬套固定倍率。用户暂停/取消后不自行重启控制。

## WF-2 数据分析与团队评审

1. 先完成 WF-1，简报包含账号背景、用户已确认约束、数据来源与窗口、证据缺口、编号问题。
2. Claude / agy / Codex 接收同一份自包含材料，首轮互相隔离、可并行；不可用方明确记缺席，不伪造团队共识。调用方式以 `loom-team-discussion` Skill 的 `run_cli_agent` 约定为准；协作手册中的 CLI 直连命令仅用于该 Tool 不可用且用户同意时的诊断，临时脚本仅在确认存在时使用。
3. **留存口径（2026-11-03 用户裁定，固定口径）**：
   - **完播率不按百分比计算，留存一律用播放时长衡量，不管原视频时长。** 后台的 `完播率` 只作平台展示值原样记录，**不参与跨篇比较，不做片长归一，也不用于反推完播次数或验证指标是否自洽**。
   - 每篇必记两个时长字段：`人均播放时长`（观众平均看了多少秒）与 `总播放时长 = 播放量 × 人均播放时长`（单位统一为秒或分钟并写明）。判断「看得久不久」看这两个数，不看百分比。
   - 同平台内可比秒数，**不跨平台混算**：同一条作品在视频号与小红书的人均时长口径不同（实证：EP16 视频号 23.85 秒、小红书 5 秒），只做各自纵向比较。
   - 账号级数据若只有播放次数、没有时长，不得用播放次数的升降代替观看时长的结论；账号层与单篇层分别陈述。
   - 解释上限不变：人均播放时长受片长上限约束（长片天然能积累更多秒数），秒数高只说明「看得久」，不能直接推出「内容更好」或「留存提升」，需同龄锚点与来源结构补证。
   - **触达与留存拆开报（用户 2026-11-04 裁定）**：触达看 `播放量`，留存看 `人均播放时长` 与 `总播放时长`，两维分别判定、分别留痕，**不合并成单一「好/不好」结论**；账号层只有播放次数时只参与触达线；判据须在观察时点前固定，事后不得调整，旧判据不改写。
4. buddy 交叉验证，分别标出事实、推测、共识、分歧与建议。数据能澄清的先查数据；平台机制无依据不得说成定论。
5. 制作决策先交 Team 讨论，再把共识及分歧交用户确认；全票/多数票不是执行授权。用户已确认方案内的动作按约执行。
6. 将讨论、用户决定与执行状态分别写入 `EP讨论/` 对应记录；后续决定追加覆盖说明，不抹去旧观点。
