## 2. 双结局成立吗？失败版怎么剪不泄气？

**成立，但应当是“双结果出口”，不是“成功与失败同样算成功”。**

成功版证明：上传和逐项读回的目标达成。

失败版最多证明两件事：

1. 这一轮没有完成目标；
2. 若证据充分，失败即停的规则确实被执行。

**不能把失败包装成“其实也是成功”，也不能把一个 BLOCKED 包装成硬件故障。**

失败版建议按这个顺序剪：

> **哪里没过 → 前面已经确认了什么 → 后面确实没再做什么 → 还不能下什么结论。**

例如，只有在实录支持时，才能说：

> “第N个文件读回不一致。此前已有K个文件完成读回校验。这一轮就停在这里，没有重试，也没有继续上传。”

这里 **K不必等于N−1**，必须以实际逐项结果为准。

失败版不泄气，靠的是**明确收获**，不是励志旁白：

- 把具体失败阶段放大，而不是滚动一屏红日志。
- 保留停止后的证据，而不只剪出错误出现的一瞬间。
- 结尾提出一个由证据直接引出的新问题，而不是泛泛地说“下次一定成功”。

还要分清失败类型：**前置未就绪、碰撞检查不通过、上传失败、读回不一致、validator 未通过**，不是同一种结局。如果根本没开始上传，就不能套“传到第N个”的模板。

## 3. 哪个标题最强？成功、失败各给一个

两个成功预案中，我选：

**《逐个读回，77个文件全对上》**

它比“一个不差传上了”强：既交代规模，也交代证明方法，更贴近本集的独特价值。标题里的“全对上”，必须由**77项逐文件精确字节读回一致**支撑，不能仅凭数量相同、总字节数相同或 validator 的 COMPLETED。

我的最终推荐：

- **成功版：《逐个读回，77个文件全对上》**
- **失败版：《第N个没过，后面没再传》**

## 7. 其他必须修改的风险点

### P0：先核实完整流程，再锁分镜

草案把“基线 → 单击 → 上传 → 读回 → COMPLETED”串成了一条因果链，**材料并未充分支持这个顺序**。

拍摄前必须依据实际实现和协议核清：

- 上传、launcher最后传、GET-only确认各发生在什么阶段；
- 单击触发的到底是哪一步；
- 哪个实例允许写，哪个实例只能GET；
- 哪份输出分别证明上传、读回和validator结果。

这是查清既有机制，不是另造流程。

### P0：三个计数不能混成一个

- **149候选 → 77文件清单：** 77是本轮确定范围，不是149项全通过。
- **73 syntax + 66 require：** 是两类validator检查项，不是139个上传文件。
- **≤83 GET：** 是确认流程预算，不是整场上传流程请求总量。

80 GET基线之后，预算最多只剩3 GET。**不能为了录屏效果额外刷新、轮询或反复取报告。**

### P0：先证明本集目标，再展示 COMPLETED

建议成功证据分三层展示：

1. **本轮固定清单：77项。**
2. **逐文件写前碰撞检查、上传、精确字节读回的结果。**
3. **validator结果：73项syntax、66项require。**

不要只放一个大大的 `COMPLETED`，把真正的问题藏在脚注里。

### P0：一次真实单击，不能为补镜重做

拍摄应提前准备好。若现场单击画面不理想，**使用可核实的同轮记录补充说明，不要求用户再点一次**。真实单击、主机接收确认、设备物理触摸是不同证据，不能互相替代。

### P1：失败原因与停止动作分开说

- 碰撞被拦，不必然代表传输能力失效。
- 请求超时，不等于设备损坏。
- BLOCKED，不等于硬件坏。
- READY，不等于触摸或Runtime验收通过。
- 没有继续上传，不自动证明“没有重试、清理、重启”；这些须分别由可用记录支持。

### P1：片尾只留一个下一问

“Works可见吗？要运行吗？”同时跨了可见性和运行两层验收，还可能让不懂“Works”的观众掉线。

建议本集结尾只问：

> **“传完了，设备里能看见吗？”**

但如果本轮素材已经证明可见，就不要明知故问，应改成下一项真正未验证的问题。

理由是：“传上设备”只回答了动作有没有完成；“逐个读回一致”才回答观众真正关心的“有没有漏、有没有变”。这也更准确地兑现 EP09 的“只上传，精确读回”。

但有两层限制：

- **选题成立，不等于结果已成立。** live 驱动和 HTTP 适配器尚未完成、尚未独立审阅，当前不能把“真机传输成功”写成事实。
- “真机”需由实际 live session 支撑，不能用 mock、回放或驱动测试画面替代证明。

**没有比它更强、且已由现有材料确证的下一集主线。** 153/154 的“39项测试、释放217MB”目前只是工程结果，没有给出足够鲜明的用户问题与转折，不适合为了守更而抢走 EP10。

如果必须在 session 前输出内容，更诚实的备选问题是：

> 为什么这次不能直接开始上传？

但现有材料只足够说明“还缺前置实现和审阅”，不足以支撑一条有过程、有结论的40秒正片。**不建议硬做。**

## 2. 双结局成立吗？失败版怎么剪不泄气？

**成立，但应当是“双结果出口”，不是“成功与失败同样算成功”。**

成功版证明：上传和逐项读回的目标达成。

失败版最多证明两件事：

1. 这一轮没有完成目标；
2. 若证据充分，失败即停的规则确实被执行。

**不能把失败包装成“其实也是成功”，也不能把一个 BLOCKED 包装成硬件故障。**

失败版建议按这个顺序剪：

> **哪里没过 → 前面已经确认了什么 → 后面确实没再做什么 → 还不能下什么结论。**

例如，只有在实录支持时，才能说：

> “第N个文件读回不一致。此前已有K个文件完成读回校验。这一轮就停在这里，没有重试，也没有继续上传。”

这里 **K不必等于N−1**，必须以实际逐项结果为准。

失败版不泄气，靠的是**明确收获**，不是励志旁白：

- 把具体失败阶段放大，而不是滚动一屏红日志。
- 保留停止后的证据，而不只剪出错误出现的一瞬间。
- 结尾提出一个由证据直接引出的新问题，而不是泛泛地说“下次一定成功”。

还要分清失败类型：**前置未就绪、碰撞检查不通过、上传失败、读回不一致、validator 未通过**，不是同一种结局。如果根本没开始上传，就不能套“传到第N个”的模板。

## 3. 哪个标题最强？成功、失败各给一个

两个成功预案中，我选：

**《逐个读回，77个文件全对上》**

它比“一个不差传上了”强：既交代规模，也交代证明方法，更贴近本集的独特价值。标题里的“全对上”，必须由**77项逐文件精确字节读回一致**支撑，不能仅凭数量相同、总字节数相同或 validator 的 COMPLETED。

我的最终推荐：

- **成功版：《逐个读回，77个文件全对上》**
- **失败版：《第N个没过，后面没再传》**

均不带集数，均不超过20字。失败标题中的 N 必须换成实录序号，且确有证据表明后续未继续上传。

如果失败发生在上传前，直接换标题，**不要为了保留模板编出一个N**。

反对原案“它自己停了”：**它隐含自动停止的因果与机制。** 如果实际是操作者看到异常后停止，这个标题就失实。

## 4. 40秒结构与留存：S2会不会赶人？

**会。不是规则不能讲，而是第二幕就要求观众学习协议，代价太高。**

“400请求 / 240秒 / 失败即停”里，只有“失败即停”直接构成戏剧张力。前两个数字应当主要作为屏幕角标或证据卡，而不是口播主干。

建议由8镜头压成6段：

| 时段 | 内容 | 关键处理 |
|---|---|---|
| 0–3秒 | 本轮实际结果或停止点 | 成功、失败分别剪；不做虚构结果闪前 |
| 3–7秒 | 问题与赌注 | “传进去还不算，要逐个读回来。” |
| 7–12秒 | 本轮操作条件 | 展示经核实的流程位置；窗口、等待用准确标注压缩 |
| 12–25秒 | 上传与读回证据 | 选一个能看懂的文件案例，再呈现全量统计；按实际顺序剪 |
| 25–34秒 | 全量结果或具体失败点 | 成功显示逐项完成范围；失败显示停止边界 |
| 34–40秒 | 本集结论与下一问 | 未做触摸/Runtime验收；下一问只留一个 |

规则的呈现建议：

- 主口播只说：**“每个文件都要读回来；一处没过，这轮就停。”**
- 在相关画面出现时标注：`请求上限400｜上传时限240秒`。
- 失败时再让“失败即停”成为主画面，而不是开头提前宣读制度。

**80 GET 基线和120秒确认窗口不应抢占主要叙事。** 但真实单击作为必要证据要保留，而且不能用点击动画替代。

同时注意：

- **120秒是确认窗口，不代表实际等了120秒。**
- 35秒 settle 与确认窗口不是同一段等待。
- 不能把上传阶段的240秒上限包装成整场 session 的总耗时。
- “逐文件上传滚动 → 最后统一精确读回”的剪法可能掩盖实际逐文件校验顺序，必须服从执行日志。

以上是编辑判断，不是已经经过留存数据验证的结论。

## 7. 其他必须修改的风险点

### P0：先核实完整流程，再锁分镜

草案把“基线 → 单击 → 上传 → 读回 → COMPLETED”串成了一条因果链，**材料并未充分支持这个顺序**。

拍摄前必须依据实际实现和协议核清：

- 上传、launcher最后传、GET-only确认各发生在什么阶段；
- 单击触发的到底是哪一步；
- 哪个实例允许写，哪个实例只能GET；
- 哪份输出分别证明上传、读回和validator结果。

这是查清既有机制，不是另造流程。

### P0：三个计数不能混成一个

- **149候选 → 77文件清单：** 77是本轮确定范围，不是149项全通过。
- **73 syntax + 66 require：** 是两类validator检查项，不是139个上传文件。
- **≤83 GET：** 是确认流程预算，不是整场上传流程请求总量。

80 GET基线之后，预算最多只剩3 GET。**不能为了录屏效果额外刷新、轮询或反复取报告。**

### P0：先证明本集目标，再展示 COMPLETED

建议成功证据分三层展示：

1. **本轮固定清单：77项。**
2. **逐文件写前碰撞检查、上传、精确字节读回的结果。**
3. **validator结果：73项syntax、66项require。**

不要只放一个大大的 `COMPLETED`，把真正的问题藏在脚注里。

### P0：一次真实单击，不能为补镜重做

拍摄应提前准备好。若现场单击画面不理想，**使用可核实的同轮记录补充说明，不要求用户再点一次**。真实单击、主机接收确认、设备物理触摸是不同证据，不能互相替代。

### P1：失败原因与停止动作分开说

- 碰撞被拦，不必然代表传输能力失效。
- 请求超时，不等于设备损坏。
- BLOCKED，不等于硬件坏。
- READY，不等于触摸或Runtime验收通过。
- 没有继续上传，不自动证明“没有重试、清理、重启”；这些须分别由可用记录支持。

### P1：片尾只留一个下一问

“Works可见吗？要运行吗？”同时跨了可见性和运行两层验收，还可能让不懂“Works”的观众掉线。

建议本集结尾只问：

> **“传完了，设备里能看见吗？”**

但如果本轮素材已经证明可见，就不要明知故问，应改成下一项真正未验证的问题。

---

**最终意见：有条件通过选题，退回当前分镜。** 保留77文件与双结果出口，弱化协议宣讲；先核清上传、读回、单击确认的真实关系，再按实际结果剪。**宁可顺延，也不要让“按协议应该发生”变成“镜头里已经发生”。**
