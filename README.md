## Runtime prerequisites
































































ESP-Claw firmware must include the Lua `storage`, `json`, `lvgl`, `board_manager`, and (for GPIO Apps) `gpio` modules.
































































Writable paths intentionally use the official storage root abstraction instead of hard-coding `/fatfs`:
































































```lua
local storage = require("storage")
local root = storage.get_root_dir()
```
































































## Deployment sketch
































































Provision the stable `bootstrap.lua` once. For the first install, use `provision/install_initial.lua` to create immutable release `0.1.0`; later Runtime releases live under `<DATA_ROOT>/clawos-runtime/releases/<version>/`. Bootstrap loads the selected release and configures `package.path` so it can `require("core.paths")`, `require("core.apps")`, etc. Put installed App packages under:
































































```text
storage.get_root_dir()/clawos/apps/<app_id>/
```
































































Run the seed/core tests first, then `main.lua` for the interactive launcher.
































































## Current notes
































































- A broken third-party manifest is isolated and does not stop ClawOS.
- Duplicate manifest IDs are rejected.
- App entry/service paths may not be absolute or contain a `..` segment.
- Per-App sandbox blocks `io`, `os`, `debug`, `package`, `loadfile`, `dofile`, and native hardware modules.
- Navigation is queued so an LVGL callback never synchronously destroys its own App tree.
- Managed timers and GPIO handles are owned by ResourceRegistry and released on App exit.
- Sensors use logical IDs registered by board adapters rather than binding Apps to specific driver module names.
- Notifications are rendered by the system layer, not by App-owned LVGL objects.
- `api/system.lua` intentionally keeps board-specific telemetry adapter-driven.
- The default Timer clock currently uses `os.clock()` behind an injectable backend. Replace it with the board/runtime monotonic clock after hardware validation without changing the App API.

- `update/release_client.lua` — query and validate the canonical release service.

- `update/README.md` — Runtime OTA architecture and operational rules.
- `update/release-manifest.example.json` — example server release manifest.
- `main.lua` — accepts bootstrap context, confirms a pending healthy release, and returns cleanly to bootstrap on soft restart.
- `provision/install_initial.lua` — one-time staging/validation/activation of Runtime `0.1.0`.
- `provision/runtime_files.lua` — explicit initial Runtime payload.
































































Device runtime layout:
































































```text
<DATA_ROOT>/clawos-runtime/
├── state.json
├── releases/<version>/
└── staging/<version>/
```
































































Normal ClawOS Runtime updates do not replace ESP-IDF/ESP-Claw firmware and do not touch `<DATA_ROOT>/clawos/apps` or `appdata`.
































## Network Foundation
































System-only shared transport is now under:
































```text
system/net/
├── errors.lua
├── http_client.lua
├── download.lua
├── websocket_client.lua
└── adapters/
    ├── espclaw_http.lua
    └── espclaw_websocket.lua
```
































HTTP is backed by ESP-Claw's `http_request` Capability through the Lua `capability` bridge. Runtime OTA uses `update/runtime_backend.lua`.
































WebSocket has a stable ClawOS client/backend contract, but the current verified ESP-Claw public Lua module catalog does not expose a generic WebSocket client; the adapter therefore fails explicitly with `E_NET_UNSUPPORTED` until a verified backend exists.

## P0.2 — Async Update Worker and Strict Versioning
















New system-only modules:
















```text
core/
└── runtime_version.lua








system/async/
└── espclaw_jobs.lua
















core/
└── update_async.lua
















update/
└── async_install_worker.lua
```
















Runtime release versions are validated by `core/runtime_version.lua`. The server canonical rules live in `update/VERSIONING.md` and `update/release-manifest.schema.json`. Runtime updates are forward-only; rollback continues to use the locally installed previous release.
















ESP-Claw async update flow:
















```text
ClawOS UI State
  -> update_async.start_latest(query)
  -> lua_run_script_async
  -> separate Lua State: async_install_worker.lua
  -> release_client.latest()
  -> HTTP 200 manifest / 204 no update
  -> HTTPS download + declared size + Lua validation
  -> pending_version
  -> main.lua observes pending state
  -> clean soft restart
  -> bootstrap loads candidate
```
















The UI/LVGL Lua State performs no HTTP or release-file I/O during the update.

## Initial Runtime Provisioning


Use `provision/install_initial.lua` only on a clean device. It copies the explicit Runtime payload into `staging/provision-0.1.0`, syntax-checks every Lua file, atomically renames the release directory, and only then writes `state.json` with active/last-good version `0.1.0`.


`bootstrap.lua` remains outside versioned releases and now passes `bootstrap_version` into each Runtime boot context.


After provisioning, run `tests/runtime_provision_check.lua`. For the real OTA smoke test, run `tests/runtime_ota_device_start.lua` against the configured update host. The foreground `update_async.poll()` treats persisted `pending_version` as authoritative, so a candidate installed by another system Lua State still triggers the clean ClawOS soft restart.
